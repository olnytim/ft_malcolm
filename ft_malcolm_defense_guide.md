## 1. Как запускать (шпаргалка)

```
sudo ./ft_malcolm <source_ip> <source_mac> <target_ip> <target_mac>
```

- `source_ip`  — IP, который выдаём за свой (его подменяем).
- `source_mac` — поддельный MAC, который привяжется к source_ip.
- `target_ip`  — IP жертвы (её ARP-таблицу травим).
- `target_mac` — настоящий MAC жертвы.

Правила: нужен `sudo`; MAC — 6 групп hex через `:` **без пробелов**; октеты IP ≤ 255.

Узнать свои/чужие адреса:
```
ip addr           # свой IP, MAC, имя интерфейса
ip neigh show     # MAC-адреса соседей
arp -a            # то же, классически
```

Бонус-флаги: `-v` (hex-дамп кадров), `-r` (непрерывное отравление), `--interval N` (период), `-i iface` (выбор интерфейса).

## 2. Как демонстрировать на защите (по оценочному листу 42)

Нужны **две машины в одной подсети**: твоя VM (атакующий) и «жертва» (хост или вторая VM). Заранее собери проект и проверь весь сценарий.

### Тест 1 — User permissions check
```
./ft_malcolm                      # без sudo, без аргументов
sudo ./ft_malcolm                 # root, без аргументов
```
- Без root → сообщение, что нужны root-права.
- Root без аргументов → usage.
Наш вывод: `you must run this program as root...` и `Usage: ...`.

### Тест 2 — Spoof between host and guest (главный)
На жертве узнай её IP и MAC (`ifconfig` / `ip addr`). Затем на атакующем:
```
sudo ./ft_malcolm <моя_VM_ip> aa:bb:cc:dd:ee:ff <IP_жертвы> <MAC_жертвы>
```
Программа **ждёт**. На жертве спровоцируй ARP-запрос про source_ip:
```
ping -c 3 <моя_VM_ip>
```
Программа поймает запрос, пошлёт reply, выйдет. На жертве проверь:
```
arp -a
```
Напротив source_ip должен стоять `aa:bb:cc:dd:ee:ff`. ✅

### Тест 3 — Program behaviour (через tcpdump)
На жертве (или третьем терминале) в отдельном окне:
```
sudo tcpdump -vv -i <interface> arp
```
Запусти ту же команду, что в тесте 2. Покажи эксперту: reply уходит **только после** появления запроса в сети, не раньше. Мы блокируемся на `recvfrom` и молчим, пока не придёт подходящий запрос.

### Тест 4 — Error management
```
sudo ./ft_malcolm 10.11.11.11 aa:bb:cc:dd:ee:ff 10.11.11.1111 aa:bb:cc:dd:ee:ff
sudo ./ft_malcolm 10.11.11.11 aaa:bb:cc:dd:ee:ff 10.11.11.11 aa:bb:cc:dd:ee:ff
```
Оба — короткие сообщения об ошибке и выход. ✅

### Плюс покажи проверки качества
```
valgrind --leak-check=full ./ft_malcolm ...   # 0 leaks, 0 errors
```
и Ctrl+C во время ожидания → чистый `Exiting program...`.

## 3. Теоретическая база (объясни это своими словами)

### OSI и где живёт ARP
Модель OSI — 7 слоёв. Нас интересуют:
- **L3 (сетевой)** — IP-адреса, маршрутизация между сетями.
- **L2 (канальный)** — MAC-адреса, доставка кадров внутри одного сегмента (LAN).

Внутри локальной сети данные ходят по MAC-адресам. Но приложения оперируют IP. **ARP** (Address Resolution Protocol, RFC 826) — мост между L3 и L2: он находит MAC по известному IP.

### Как работает ARP
1. Хост A хочет отправить пакет на IP `10.0.0.5`, но не знает его MAC.
2. A шлёт **ARP request** в broadcast (на `ff:ff:ff:ff:ff:ff`): «Who has 10.0.0.5? Tell 10.0.0.3».
3. Владелец `10.0.0.5` отвечает **ARP reply** (unicast): «10.0.0.5 is at aa:bb:...».
4. A кладёт пару `IP→MAC` в **ARP-кэш** (таблицу) и дальше шлёт кадры на этот MAC.

### Уязвимость (почему атака работает)
ARP **не имеет аутентификации**. Хост верит любому reply, даже если:
- он его не запрашивал (gratuitous ARP);
- MAC в ответе поддельный.

Значит, мы можем ответить на чужой запрос своим MAC. Жертва запишет `source_ip → наш_поддельный_MAC` и начнёт слать трафик для source_ip не туда, куда надо — это и есть Man-In-The-Middle.

Наш сценарий (по сабджекту) узкий: дождаться, пока **сама жертва** спросит про source_ip, и подсунуть ответ.

### Порядок байт (byte order)
В сети байты идут в **big-endian** (network order): старший байт первым. x86/ARM — **little-endian**. Поэтому многобайтовые поля (тип Ethernet, opcode ARP) перед отправкой конвертируем:
- `htons` — host-to-network short (16 бит),
- `ntohs` — обратно.
Однобайтовые поля (`hlen`, `plen`) порядка байт не имеют. IP-адреса `struct in_addr` уже хранятся в network order (так их пишет `inet_pton`).

### Raw-сокеты L2 (почему AF_PACKET)
Обычный сокет `AF_INET` работает с L3/L4 (IP/TCP/UDP) — ядро само строит Ethernet-заголовок. Нам нужно самим собрать **весь Ethernet-кадр** и работать с ARP (L2). Для этого Linux даёт:
```
socket(AF_PACKET, SOCK_RAW, htons(ETH_P_ARP))
```
- `AF_PACKET` — сырой доступ на канальном уровне;
- `SOCK_RAW` — получаем/шлём кадр целиком, включая Ethernet-заголовок;
- `htons(ETH_P_ARP)` — фильтр: ядро отдаёт нам только ARP-кадры.
Это Linux-специфично (на macOS/BSD аналог — BPF), поэтому проект собирается только под Linux. Нужен root (raw-сокеты требуют привилегий).

### Структура кадра (42 байта)
```
Ethernet (14 б): dst_mac[6] | src_mac[6] | type[2]=0x0806(ARP)
ARP     (28 б): htype[2]=1(Ether) | ptype[2]=0x0800(IPv4) | hlen=6 | plen=4 |
                 oper[2]=1req/2reply |
                 sha[6] sender-mac | spa[4] sender-ip |
                 tha[6] target-mac | tpa[4] target-ip
```
14+28 = **42 байта**. Минимальный Ethernet-кадр — 60 байт, ядро само добьёт нулями при отправке.

## 4. Разбор кода (файл за файлом, «как будто писал я»)

Структура: `main.c` (оркестрация) → `args.c` (валидация) → `net.c` (сеть) → `arp.c` (логика ARP) → `utils.c` (помощники). Заголовок `ft_malcolm.h` — общие типы и прототипы.

### ft_malcolm.h
- Инклюды сетевых заголовков + libft. `#ifndef`-защита констант `ETH_P_ARP` и т.д. на случай отсутствия в системных заголовках.
- `t_arp_frame` — **packed**-структура кадра. `__attribute__((packed))` запрещает выравнивание, чтобы структура точно легла в 42 байта провода.
- `t_malcolm` — единственная глобальная структура состояния (одна разрешённая глобальная переменная). Держит сокет, интерфейс, разобранные адреса, бонус-флаги.
- `extern t_malcolm g_malcolm;` — объявление; определение в `main.c`.

### main.c
- `g_malcolm` — определение глобалки.
- `usage()` — печать формата в stderr.
- `handle_sigint()` — обработчик Ctrl+C. Использует **только async-signal-safe** вызовы: `write` (печать), `close` (закрыть сокет), `_exit` (мгновенный выход без сброса буферов). Почему не `printf`/`exit`? Их нельзя безопасно звать из обработчика сигнала. Именно поэтому в остальном коде стоят `fflush(stdout)` — чтобы вывод не потерялся, раз `_exit` не сбрасывает буфер stdio.
- `setup_signals()` — регистрирует обработчик через `sigaction(SIGINT, ...)` (предпочтительнее `signal`).
- `main()` — порядок:
  1. обнулить состояние, `sockfd = -1`;
  2. `parse_arguments` — валидация (до проверки root, чтобы невалидные аргументы ловились всегда);
  3. `getuid() != 0` → ошибка про root;
  4. `find_interface` → выбрать интерфейс;
  5. `open_socket` → создать raw-сокет;
  6. `setup_signals`;
  7. `wait_for_request` → `send_reply`;
  8. если `-r` → `persist` (бонус);
  9. закрыть сокет, `Exiting program...`.

### args.c
- `parse_decimal_ip` (бонус) — IPv4 одним 32-битным числом. Считаем цифры вручную в `unsigned long` (ft_atoi не держит >INT_MAX), проверяем переполнение 32 бит, затем **вручную раскладываем 4 байта в big-endian** (без `htonl`).
- `parse_ip` — три попытки по порядку: `inet_pton` (точки) → decimal → `getaddrinfo` (имя хоста, бонус). При провале — точный текст сабджекта `unknown host or invalid IP address`. `getaddrinfo` освобождаем через `freeaddrinfo` (нет утечки).
- `hex_value` — символ hex → значение или -1.
- `parse_octet` — один октет MAC (1–2 hex-цифры), двигает указатель. Возвращает -1, если 0 цифр или после них снова hex (значит октет длиннее 2).
- `parse_mac` — строго 6 октетов, ровно 5 двоеточий, без хвоста. Иначе `invalid mac address`.
- `parse_interval` (бонус) — строго положительное число секунд.
- `flag_eq` — точное сравнение флага через `ft_strncmp(a, flag, ft_strlen(flag)+1)` (сравниваем и завершающий `\0`, чтобы `-v` не совпало с `-verbose`). Обходит сломанный `ft_strcmp`.
- `handle_flag` — распознаёт `-v/-r/-i/--interval`; флаги со значением сдвигают индекс. Неизвестный флаг → usage.
- `parse_arguments` — разделяет флаги и ровно 4 позиционных аргумента, потом валидирует их через `parse_ip`/`parse_mac`.

### net.c
- `is_usable` — годится ли интерфейс: должен быть `AF_PACKET` (канальный адрес с MAC), не loopback, `UP` и `RUNNING`. Если задан `-i` (бонус) — просто совпадение по имени.
- `find_interface` — `getifaddrs` перебирает интерфейсы; для первого подходящего берём имя, индекс (`if_nametoindex`) и MAC (из `sockaddr_ll->sll_addr`), печатаем `Found available interface: ...`, освобождаем список `freeifaddrs`.
- `open_socket` — создаёт `socket(AF_PACKET, SOCK_RAW, htons(ETH_P_ARP))`. **Bind не делаем**: приём фильтруем по содержимому во `wait_for_request`, а отправку адресуем через `sll_ifindex` в `sendto`.

### arp.c
- `is_target_request` — совпадает ли принятый кадр с ожидаемым: это ARP-**request** (`oper==1`), отправитель (`spa`) = target_ip, спрашиваемый (`tpa`) = source_ip. Сравнения `eth_type`/`oper` идут против `htons(...)`, т.к. в кадре они в network order. IP сравниваем `ft_memcmp` (in_addr тоже в network order).
- `announce_request` — печатает MAC и IP отправителя запроса (как в примере сабджекта); при `-v` — hex-дамп.
- `wait_for_request` — цикл `recvfrom` в буфер 64 КБ. Короткие кадры (< 42 б) пропускаем; `EINTR` — повторяем; при совпадении — печатаем и выходим. Сокет уже фильтрует по ETH_P_ARP, так что приходят только ARP-кадры.
- `build_reply` — заполняет reply: `eth_dst`=target_mac, `eth_src`=source_mac (подделка), `oper`=reply, `sha`=source_mac, `spa`=source_ip, `tha`=target_mac, `tpa`=target_ip. Смысл: «source_ip находится по source_mac».
- `raw_send` — общий отправитель. Заполняет `sockaddr_ll` назначения (`sll_ifindex`, `sll_halen=6`, `sll_addr`=target_mac) и шлёт 42 байта через `sendto`.
- `send_reply` — mandatory: печатает баннер, зовёт `raw_send`, печатает «Sent...».
- `persist` (бонус `-r`) — каждые `interval` секунд снова шлёт reply (`sleep` разрешён), пока не Ctrl+C.

### utils.c
- `error_msg` — печать ошибки в stderr в формате `ft_malcolm: <msg>: (<arg>).`; всегда возвращает 1 (удобно `return (error_msg(...));`).
- `mac_to_string` — 6 байт → строка `aa:bb:...` через `sprintf` (входит в «printf и семейство»).
- `print_hex_dump` (бонус) — offset + hex + ASCII, для `-v`.

## 5. Вопросы эксперта и ответы

- **Почему одна глобальная переменная?** Сабджект разрешает одну; она нужна, чтобы обработчик Ctrl+C дотянулся до сокета и закрыл его. Всё состояние держим в одной структуре.
- **Почему AF_PACKET, а не AF_INET?** ARP живёт на L2; нужно собрать весь Ethernet-кадр. AF_INET работает с L3+ и сам строит заголовки — для ARP не подходит.
- **Зачем root?** Raw-сокеты требуют привилегий (CAP_NET_RAW). Иначе `socket()` вернёт ошибку.
- **Что делает htons?** Переводит 16-битное поле из порядка хоста в сетевой (big-endian). Нужно для `eth_type`, `oper` и фильтра протокола.
- **Зачем packed-структура?** Чтобы компилятор не вставил padding и структура точно совпала с 42 байтами на проводе.
- **Почему запрос шлёт именно жертва?** По сабджекту мы пассивны: ждём, пока target сам спросит про source_ip, и отвечаем. Так мы отравляем его кэш ровно в нужный момент.
- **Почему 42 байта?** 14 (Ethernet) + 28 (ARP для IPv4/Ethernet). Минимум кадра 60 — ядро добьёт нулями.
- **Зачем нужен bind?** Не нужен: приём фильтруем по содержимому, отправку адресуем через ifindex. Поэтому bind убран (его и нет в списке разрешённых функций).
- **Как защититься от ARP-спуфинга?** Статические ARP-записи; Dynamic ARP Inspection (DAI) на управляемых свитчах; DHCP snooping; шифрование выше L2 (VPN/TLS), чтобы перехват был бесполезен.
- **Утечки/краши?** Проверено valgrind: 0 leaks, 0 errors. Весь heap (`getifaddrs`/`getaddrinfo`) освобождается.
